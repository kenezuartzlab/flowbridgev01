## 6. Deployer address and secure signing transport

Transport is external-wallet only (`src/lib/deploy/deploymentTransport.ts`): Lovable prepares the unsigned transaction, the operator's own wallet signs on chain 677. The model contains **no** private-key, seed, keystore or signing-secret field (enforced by test), no admin endpoint returns signing material, and a wallet connection can never auto-broadcast. States: `NO_SIGNER → SIGNER_CONNECTED → CHAIN_VERIFIED → FUNDED → STAGE_APPROVED`. Safe/protocol-role addresses are rejected as deployer; the deployer receives no permanent role.

## 9. Stage approval model (A–G)

One-time approvals bind stage, candidate digest, manifest hash, chain 677, deployer address, artifact creation hash, constructor-argument hash and expected effect into a `bindingHash`. Any change invalidates; approval is consumed after broadcast or cancelled manually; a revert never re-authorizes altered calldata; deployment approval never authorizes funding (`G_FUNDING` is separate).

## 11. DRY_RUN deployment state machine

`runDeploymentDryRun()` executes the full lifecycle on real frozen artifacts with `broadcasts = 0`; `eth_sendRawTransaction`, `wallet_sendTransaction` and Safe execution are unreachable. Happy path advances all five stages `NOT_DEPLOYED → BROADCASTED → RECEIPT_CONFIRMED → BYTECODE_MATCHED → SOURCE_VERIFIED → DEPLOYED_VERIFIED` in dependency order. Simulated failures each stop progression at the correct state: missing receipt, reverted receipt, unreadable/ mismatched runtime hash, failed explorer verification, wrong role, changed Safe state. Funding (`UNFUNDED → FUNDING_APPROVED → FUNDED_READY`) and feature state (`PENDING_POOL`) never advance from deployment progress.
