# Rewards rules
- Payout schedule proposals use scheduleRenewal.ts and service-only reward_schedule_renewals overlays; explicit approval supersedes previous schedules without modifying base batches, and acquire_reviewed_reward_publication binds fingerprint/calldata under batch-first locks. Why: repeat renewal must preserve history and never race a broadcast.
- Payout background reconciliation uses payoutRecovery.server.ts to verify exact nonce/receipt/round and reconcile_reward_publication for atomic system-attributed confirmation; scheduled access requires REWARDS_SWEEP_SECRET. Why: a public key must never authorize private audit writes or duplicate sends, and recovery must not impersonate a disabled operator.
- Existing unsigned batches are selected and revalidated through immutableBatch.ts against fresh funded eligibility and live contract timing; reads never overwrite their fingerprint, window or allocation. Why: hourly preview fingerprints previously diverged from stored immutable records and hid expired windows.
- Existing approved policy versions are validated by approvedRewardPolicy.ts; policy drift fails closed, and reviewed historical milestones are excluded by row/date in historicalReconciliation.ts. Why: later activity must never silently restore a historical hold or change economics under the same version.
- Historical reconciliation explains aggregate differences exactly covered by excluded provenance-held ledger rows without admitting those rows or changing permanent historical restrictions. Why: unrelated held/unfunded earnings must not veto an independently accepted and funded payout subset.
- Reward insert guards serialize wallet/day and referrer/month caps in PostgreSQL; historical rows are not rewritten. Why: separate concurrent events can bypass a read-then-insert cap.

- Reward balance/readiness presentation uses rewardPresentation.ts from caller-scoped RewardProgression, never legacy claimableTotal or stored aggregate subtraction. Why: earned points and published on-chain claims are different stages.

- Reward-processing failures are recorded via src/lib/rewards/rewardDiagnostics(.server).ts into server-only reward_processing_events; economic ledgers are writable only by service_role and profile guard triggers run SECURITY INVOKER. Why: a silent persistence failure and a definer-owner guard bypass previously went unnoticed.
- Reward funding is reserved only through SECURITY DEFINER RPCs (award_signup_bonus, increase_reward_budget) against reward_budgets; only FUNDED ledger rows count toward 1:1 FLOW claims, and the 1:1 claim gate lives in src/lib/rewards/signupBonusPolicy.ts. Why: points equal tokens, so every point must be backed and never derived from profile aggregates.
- Historical FLOW Points reconciliation and per-program solvency are computed only in src/lib/rewards/historicalReconciliation.ts and rewardFundingPlan.ts (pure), served admin-only via /api/admin/rewards-solvency to the /ops Rewards tab. Why: stored profile aggregates were once user-writable and must never authorize claims.
- The Mainnet claim minimum and its single canary exception are decided only in src/lib/rewards/claimMinimumPolicy.ts, applied by buildDraftAllocation and the Earn UI. Why: the payout contract enforces no on-chain minimum.
- V37: new Ops-approved payout rounds (epoch 4+) require only a positive verified amount (MIN_OPS_CLAIM_FLOW = 1); historical rounds at or below epoch 3 keep the 1,000 minimum via claimMinimumForEpoch. Why: owner policy removed the waiting threshold for new payouts while preserving history.
- User payout approvals flow only through src/lib/rewards/approvalQueue(.server).ts and reward_payout_approvals (propose → different super admin approve → hash-checked confirm; immutable amount/wallet/evidence, one open proposal per account); confirmation reserves nothing new and only re-runs the prepare-only settlement builder. Why: proposer/approver separation and delta math must never double-pay or let a single operator pay out.
- Settlement batches are prepared only in src/lib/rewards/settlementPlanner.ts (pure, prepare-only, unsigned publishEpoch). Why: automation must never hold publisher keys or sign on-chain.
- Published settlement rounds after round #2 are discovered from server-stored batches (reward_settlement_batches) and served per-wallet via /api/public/reward-rounds only when the stored root equals the live on-chain root; Earn re-verifies on chain. Why: new rounds must not need a frontend release, and a wrong answer may only block, never pay.
- Published reward rounds missing a local record are indexed read-only from live chain truth in src/lib/rewards/historicalRoundIndex.ts (pure) as ON_CHAIN_HISTORICAL_IMPORT, only when a proof source reproduces the on-chain root; drift is flagged, never overwritten, and Earn discovers rounds from these records first with the built-in manifest as fallback. Why: round #2 predated the batch table and was invisible to discovery.
- Ordinary public Mainnet claims are gated only by PUBLIC_MAINNET_FLOW_CLAIMS and the lifecycle/eligibility rules in src/lib/rewards/publicClaimPolicy.ts (pure); rounds after the historical canary epoch never inherit its exception. Why: eligible must never be treated as claimable, and one switch controls rollout.
- The four reward balances, claim blocker and timeline stage come only from src/lib/rewards/rewardsSummary.ts (pure, over RewardProgression); Flow AI/opportunities read claimable FLOW only via resolveClaimableNowFlow. Why: legacy points-minus-claimed figures showed "ready to claim" without an open on-chain allocation.
- Wallets reaching the claim minimum are queued only via src/lib/rewards/settlementQueue.ts (pure, idempotent, caps + circuit breaker); publisher mode is DRY_RUN/ONE_CLICK and autonomous signing stays off. Why: automation removes busywork, never financial verification or human signing.
- One-click publishing: batch/day limits and the publisher wallet gate live only in src/lib/rewards/publishGate.ts; the operator's own wallet signs, and success is reported only after /api/admin/rewards-publish-verify confirms the receipt and on-chain round. Why: no app-held key, and broadcast is not publication.
- Signup awards (no chain id in ledger) count as BOT Mainnet only via attributeSignupAward in src/lib/rewards/signupAttribution.ts, which also requires the program's funding_verified. Why: provenance must be proven, never inferred, and unconfirmed backing must stay excluded.
- Publish outcomes are audited only after observed verification (AUDITED_PHASES in publishGate.ts) as admin_audit_events object_type reward_round; pending broadcasts are re-checked, never re-sent, and autonomous signing requires every AUTONOMOUS_ACTIVATION_REQUIREMENTS item. Why: retries must never double-publish and automation needs separate approval.
- Publisher receipt identity is validated in publicationVerification.ts and publicationRecovery.server.ts; fenced operation IDs and acquire/transition_reward_publication own retry locks, publisherReconciliation.server.ts checks recorded sender nonce before hash attachment and nonce/chain recovery, and confirm_reward_publication atomically persists confirmation/audit. Only conclusive cancellation or reconciled exact reverts permit retry; unknown broadcasts never expire. Why: wallet rejection must not strand batches or allow duplicate sends.
- Ops restores stuck publication attempts only via selectRestorableAttempt in publisherRecovery.ts, which matches any non-final, non-retry-safe attempt regardless of epoch, and cancellation evidence is persisted inside PendingPublication so a reload can still release a pre-broadcast lock. Why: a mined round advancing the live epoch counter or a page reload must never hide the recovery controls.
- Off-chain funding is proposed/approved/confirmed only through reward_funding_snapshots and the confirm_reward_funding_snapshot RPC (super admin, hash-checked, single-use), with queue eligibility decided only in src/lib/rewards/fundingQueue.ts and served via /api/admin/rewards-control to Ops → Control Center. Why: funding must never be repeated, stale or done by hand in the database.
- Ops draft previews are funded-only via summarizeFundedDraft in rewardFundingPlan.ts over the settlement readiness, with any reconciliation-vs-funded difference shown as excludedUnfundedPoints. Why: unfunded ledger points must never appear as a publishable payout amount.
- Core Swap funding and settlement require row-level verified provenance; the accrual writer independently re-ingests canonical Mainnet receipts and server pricing, while historical unproven rows remain quarantined. Why: client hints, labels and aggregate balances cannot establish earning authority.
- Historical Core Swap pricing exceptions go only through evidenceReview.ts and the propose/decide_reward_evidence_exception RPCs (different super admin decides; amount immutable; EXCEPTION_APPROVED is the only accepted non-VERIFIED provenance). Why: missing old records must have an audited path without silent release.
- Historical evidence assessment is SELECT-only through rewardEvidenceAssessment(.server).ts; diagnostic metadata never promotes provenance, and grouped reviews use atomic group RPCs retaining individual audits and live transaction/wallet/policy/limit/reservation checks. Successful group decisions recalculate unsigned eligibility/renewal only. Why: recorded prices are not historical proof, partial approval must not occur, and renewal needs separate authorization.
- Funding confirmation invokes the existing solvency/settlement preparation after commit; failure is reported separately and never repeats funding or signs. Why: distribution readiness should not require operator reconstruction or imply publication.
- V37.1: new rounds include only CONFIRMED, unlinked reward_payout_approvals capped at the approved amount; approvals are linked write-once to verified-published rounds only via link_payout_approval (approvalLinkage.ts plans, sweep/publish-verify/recovery run it). Automatic approval is program-separated via auto_approve_payout_v2 with an immutable program_breakdown; ambiguous (OTHER) points are held. Why: an approval must map to exactly one paid round, and disabled programs must never ride along.

- Revised funded automation uses auto_approve_funded_payout with a fresh chain capacity read, publisher nonce check and payout-evidence fence; routine candidates exclude historical exception approvals. The master switch is atomic and service-only; existing funded budgets and rolling-day/batch caps replace extra budget configuration. Why: automatic commitments need current unencumbered backing without repetitive approval.
- Retired unapproved drafts stay immutable in reward_settlement_batches with service-only reward_retired_drafts tombstones and publication-trigger fences; next batches are rebuilt exclusively from fresh confirmed approvals. Why: old leaves must never inherit new authorization or block the next live epoch.
- Approved batch persistence uses persist_funded_reward_batch under epoch locks; expired confirmed allocations refresh only via refresh_funded_batch_schedule under the enabled master policy, preserving base schedules. Why: concurrent preparation cannot overlap and routine expiry must not require another financial approval.
- Mid-cycle eligibility reloads pass persistBatch:false; only the final report of a cycle prepares a batch, and automation confirms already two-person-approved records via confirmApproved (publisher recipients stay held). Why: per-record rebuilds created partial batches that stranded later confirmations.
- Reserved balances blocked by account reconciliation carry reconciliationBlocked through shared progression/presentation; Ops read-only POST queries use the bounded read helper. Why: reserved funding must not imply payout eligibility, and stalled checks must terminate without retrying writes.
