# Rewards rules
- Existing approved policy versions are validated by approvedRewardPolicy.ts; policy drift fails closed, and reviewed historical milestones are excluded by row/date in historicalReconciliation.ts. Why: later activity must never silently restore a historical hold or change economics under the same version.
- Reward insert guards serialize wallet/day and referrer/month caps in PostgreSQL; historical rows are not rewritten. Why: separate concurrent events can bypass a read-then-insert cap.

- Reward balance/readiness presentation uses rewardPresentation.ts from caller-scoped RewardProgression, never legacy claimableTotal or stored aggregate subtraction. Why: earned points and published on-chain claims are different stages.

- Reward-processing failures are recorded via src/lib/rewards/rewardDiagnostics(.server).ts into server-only reward_processing_events; economic ledgers are writable only by service_role and profile guard triggers run SECURITY INVOKER. Why: a silent persistence failure and a definer-owner guard bypass previously went unnoticed.
- Reward funding is reserved only through SECURITY DEFINER RPCs (award_signup_bonus, increase_reward_budget) against reward_budgets; only FUNDED ledger rows count toward 1:1 FLOW claims, and the 1:1 claim gate lives in src/lib/rewards/signupBonusPolicy.ts. Why: points equal tokens, so every point must be backed and never derived from profile aggregates.
- Historical FLOW Points reconciliation and per-program solvency are computed only in src/lib/rewards/historicalReconciliation.ts and rewardFundingPlan.ts (pure), served admin-only via /api/admin/rewards-solvency to the /ops Rewards tab. Why: stored profile aggregates were once user-writable and must never authorize claims.
- The Mainnet claim minimum and its single canary exception are decided only in src/lib/rewards/claimMinimumPolicy.ts, applied by buildDraftAllocation and the Earn UI. Why: the payout contract enforces no on-chain minimum.
- Settlement batches are prepared only in src/lib/rewards/settlementPlanner.ts (pure, prepare-only, unsigned publishEpoch). Why: automation must never hold publisher keys or sign on-chain.
- Published settlement rounds after round #2 are discovered from server-stored batches (reward_settlement_batches) and served per-wallet via /api/public/reward-rounds only when the stored root equals the live on-chain root; Earn re-verifies on chain. Why: new rounds must not need a frontend release, and a wrong answer may only block, never pay.
- Published reward rounds missing a local record are indexed read-only from live chain truth in src/lib/rewards/historicalRoundIndex.ts (pure) as ON_CHAIN_HISTORICAL_IMPORT, only when a proof source reproduces the on-chain root; drift is flagged, never overwritten, and Earn discovers rounds from these records first with the built-in manifest as fallback. Why: round #2 predated the batch table and was invisible to discovery.
- Ordinary public Mainnet claims are gated only by PUBLIC_MAINNET_FLOW_CLAIMS and the lifecycle/eligibility rules in src/lib/rewards/publicClaimPolicy.ts (pure); rounds after the historical canary epoch never inherit its exception. Why: eligible must never be treated as claimable, and one switch controls rollout.
- The four reward balances, claim blocker and timeline stage come only from src/lib/rewards/rewardsSummary.ts (pure, over RewardProgression); Flow AI/opportunities read claimable FLOW only via resolveClaimableNowFlow. Why: legacy points-minus-claimed figures showed "ready to claim" without an open on-chain allocation.
- Wallets reaching the claim minimum are queued only via src/lib/rewards/settlementQueue.ts (pure, idempotent, caps + circuit breaker); publisher mode is DRY_RUN/ONE_CLICK and autonomous signing stays off. Why: automation removes busywork, never financial verification or human signing.
- One-click publishing: batch/day limits and the publisher wallet gate live only in src/lib/rewards/publishGate.ts; the operator's own wallet signs, and success is reported only after /api/admin/rewards-publish-verify confirms the receipt and on-chain round. Why: no app-held key, and broadcast is not publication.
- Signup awards (no chain id in ledger) count as BOT Mainnet only via attributeSignupAward in src/lib/rewards/signupAttribution.ts, which also requires the program's funding_verified. Why: provenance must be proven, never inferred, and unconfirmed backing must stay excluded.
- Publish outcomes are audited only after observed verification (AUDITED_PHASES in publishGate.ts) as admin_audit_events object_type reward_round; pending broadcasts are re-checked, never re-sent, and autonomous signing requires every AUTONOMOUS_ACTIVATION_REQUIREMENTS item. Why: retries must never double-publish and automation needs separate approval.
- Publisher receipt identity is validated in publicationVerification.ts and publicationRecovery.server.ts; server-only epoch attempts lock before wallet submission and confirm_reward_publication atomically persists confirmation/audit. Why: missing wallet context and transient RPC/UI failures must never cause a second publication.
- Off-chain funding is proposed/approved/confirmed only through reward_funding_snapshots and the confirm_reward_funding_snapshot RPC (super admin, hash-checked, single-use), with queue eligibility decided only in src/lib/rewards/fundingQueue.ts and served via /api/admin/rewards-control to Ops → Control Center. Why: funding must never be repeated, stale or done by hand in the database.
